# 专业场域的编辑基线

处理发布说明、PR / issue / 评审回复、事故复盘、工单、技术文章等专业文本时读取，适用于任何语言。让信息量、判断、格式和篇幅服从实际场域，语言表面规则仍由对应语言路径决定。

## 先确定场域基线

先写清读者打开这份文本要完成什么任务。用户已经提供同一仓库、团队、栏目或作者的 2–3 份近期样本时，用它们校准：

- 称呼、礼貌程度和第一人称习惯。
- 常用标题、模板、列表和字段。
- 正常篇幅、细节密度和术语写法。
- 结论、风险和不确定性的表达方式。

样本取自用户已提供或当前任务明确授权的范围。没有样本时使用下列场域基线，风格判断以当前文本为准。

## 共同检查

1. **读者任务：** 每段是否帮助读者决定、执行、复现、排障或评估；背景若只是复述上下文，删除。
2. **信息密度：** 删去后仍完整保留事实、关系、判断与风险的句子属于填充；篇幅随风险和复杂度变化。
3. **判断位置：** 需要结论、取舍或责任判断时，直接呈现原文已有判断；不确定性按原强度保留。
4. **具体性：** 版本、数字、时间、命令、错误文本、文件位置和引用来自原文或已授权材料。缺少时保留槽位、询问，或按原强度表述。
5. **格式功能：** 惯例模板、真实清单、步骤和字段按场域容器保护；无助于检索、执行或比较的装饰格式可以拆改。
6. **可读性：** 语法和实际场域表达同时过关；正式文字保持清楚，短回复保持礼貌。

## 场域卡片

### 发布说明、更新日志与公告

- 读者任务：判断是否升级、什么改变、是否需要迁移。
- 先保留版本、日期、破坏性变更、迁移步骤、问题编号和真实基准条件；项目原有的 Added / Changed / Fixed 等分类属于受保护容器。
- 删除“激动宣布”“无缝体验”“全面赋能”等缺少机制或数据的宣传外壳。按用户影响排序，补丁版本保持相称篇幅。
- 原文只说“性能改善”时保留该强度；基准数字来自原文或作者补充。

### PR 描述、issue / 评审回复与讨论

- 读者任务：理解结论、改动、原因、验证方式或下一步。
- 回复优先给答案或判断，再写必要理由。感谢、赞美、道歉和收尾邀请只在承担真实礼貌或关系功能时出现。
- `file:line`、commit、错误文本、测试结果和链接来自原文或授权上下文。
- 保持场域原有的严重程度标记、礼貌习惯和短答长度。直截了当可以礼貌，正式回复可以简短。

### 事故复盘、RCA 与运行报告

- 读者任务：还原影响、机制、判断过程和可执行改进。
- 保护绝对时间、时区、影响范围、失败机制、错误假设、未知项、来源和责任边界。对人保持无责，同时写清系统、角色和已经证实的因果。
- “加强监控、优化沟通”的负责人、期限和阈值来自原文；缺项时保留原判断并请求作者补齐。
- 时间线承担响应说明；多个并列因素保持原有证据关系。

### 工单、任务单与错误报告

- 读者任务：复现问题、确认期望、执行工作并验收。
- 保护标题、环境、复现步骤、实际结果、期望结果、范围、优先级和验收条件；团队模板属于场域容器。
- 标题可以在授权范围内改成明确结果，重复背景可链接或合并，执行所需字段完整保留。
- 缺少复现条件、负责人或验收标准时请求补充；字段内容以授权材料为准。

### 技术文章、教程与经验复盘

- 读者任务：理解一个真实问题、方法、限制和可复用结论。
- 模型、数据、工程和实验内容同时读取 `references/technical-writing.md`，使用标准术语、完整语义角色和直接机制描述。
- 优先保留原文已有的问题现场、失败尝试、取舍、数字及测试条件。第一人称、明确意见和局部不均匀的篇幅可以属于作者声口。
- 删除读者已知的百科式开场、章节预告和重复总结；长文同时使用 `references/narrative-patterns.md` 的段落问题检查，人物与事件仍按纪实材料保护。
- 失败经历、实验数字和立场来自原文或授权材料。

## 停手线

- 场域惯例优先于通用审美：正式公文、标准模板、规范字段和真实平行清单可以保持整齐。
- 具体但错误比概括更糟。所有新增专名、数字、命令、来源、责任人和日期都必须能回指授权材料。
- 只修实际命中的问题；句长、人称和观点强度服从场域与原文。
